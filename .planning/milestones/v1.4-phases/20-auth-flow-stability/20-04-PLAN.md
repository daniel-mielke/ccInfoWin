```csharp
    public void NavigateTo<TPage>() where TPage : Page
    {
        Debug.Assert(_frame is not null, "NavigationService.Initialize must be called before NavigateTo");

        // D-09 / AUTH-05: bring window to foreground before navigating. Zero cost when window is
        // already foreground; restores the window when minimized (e.g., during a background-poll
        // 401 → auto-reauth path). Activate() is the WinUI 3 idiom — same call used in App.OnLaunched.
        App.MainWindow?.Activate();

        _frame?.Navigate(
            typeof(TPage),
            null,
            new SlideNavigationTransitionInfo { Effect = SlideNavigationTransitionEffect.FromRight });
    }
```

Strict rules:
- The activation call MUST come BEFORE `_frame?.Navigate(...)`. Reverse order leaks a frame of "page changed but window still minimized".
- Use `App.MainWindow?.Activate()` — `App.MainWindow` is the existing static property at `App.xaml.cs:19`. The reference compiles directly because `NavigationService` is in `CCInfoWindows.Services` namespace and `App` is in the root `CCInfoWindows` namespace; the implicit using of the root namespace makes `App` reachable. If the compiler complains, add `using CCInfoWindows;` at the top of the file (do NOT add `using Microsoft.UI.Xaml;` — Window type already in scope via App).
- DO NOT add a parameterized overload — D-09 explicitly chose global behavior in the existing single method (the `NavigateAndActivate<TPage>` overload was rejected, see CONTEXT §Deferred Ideas item 4).
- DO NOT touch `Initialize`, `CanGoBack`, or `GoBack`.
- DO NOT introduce any new dependency on `App.xaml.cs` beyond reading the static property — keep the service class testable.
