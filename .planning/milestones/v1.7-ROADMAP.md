## Context

Startet Claude Code einen Workflow (`ultracode`), erscheint **kein einziger** seiner Subagents
in der KONTEXTFENSTER-Sektion. Normale Subagents (via Agent-Tool) werden korrekt angezeigt.

### Ursache

`FindSubagentFilesForSession` (`JsonlService.cs:885-908`) scannt mit
`Directory.GetFiles(subagentDir, AgentFilePattern)` — ohne `SearchOption`, also
**nur die oberste Ebene**. Die beiden Ablageformen unterscheiden sich aber in der Tiefe:

```
{projectDir}/{sessionUuid}/subagents/agent-{id}.jsonl                      ← Agent-Tool, gefunden
{projectDir}/{sessionUuid}/subagents/workflows/wf_{runId}/agent-{id}.jsonl ← Workflow, NICHT gefunden
```

Der Scan liefert für eine reine Workflow-Session null Treffer. Weil danach `result.Count == 0`
gilt, greift der Fallback auf `{projectDir}/subagents` (Zeile 896-905) — ein Verzeichnis, das
in dieser Ablage nicht existiert. Ergebnis: leere Liste, kein Log-Eintrag, keine sichtbare
Fehlermeldung. Der Bug ist **stumm**.

### Gemessene Größenordnung (2026-08-09)

| Wert | Messung |
|---|---|
| Workflow-Agent-Dateien gesamt | 67 in 7 Runs |
| Größter einzelner Run | **44 Agents** |
| Flache Subagent-Dateien | 10 |

Ein Run kann also die Zeilenzahl der Sektion vervierzigfachen. Bei ~28 px pro Zeile wären
44 Agents ≈ 1230 px in einem ~600 px hohen Fenster. Deshalb ist die Anzeige-Entscheidung
(unten) kein Kosmetik-Thema, sondern die eigentliche Substanz des Milestones.

### macOS-Referenz: kein Vorbild vorhanden

`spec/` (v1.7.1, v1.8.3, v1.10.0, v1.11.1) enthält **keinen einzigen** Treffer für „workflow".
Die Subagent-Anforderungen FA-042 und FA-062 sowie Phase 4 der v1.8.3-Spec (Sortierstabilität)
kennen ausschließlich den flachen Pfad. Workflows sind ein neueres Claude-Code-Feature als die
Referenz-App.

**Konsequenz:** Dieser Milestone ist eine Windows-Erweiterung *über* die Parität hinaus, kein
Nachzug. Es gibt kein Upstream-Design, an dem man sich orientieren müsste oder von dem man
abweichen würde.

### Ausdrücklich NICHT im Scope

- **Agent-Namen aus `.meta.json`.** Neben jeder `agent-*.jsonl` liegt eine bisher ungenutzte
  Metadatei — normal `{"agentType":"Explore","description":"Map chart implementation",…}`,
  Workflow `{"agentType":"workflow-subagent","spawnDepth":1}`. Sie würde erlauben, endlich
  echte Namen statt Hex-IDs zu zeigen. Bewusst ausgelassen: die gewählte Aggregat-Darstellung
  braucht keine Namen, und das Lesen kostete 44 Dateiöffnungen pro Poll-Tick. Bleibt als
  Option, falls die Einzelagenten-Ansicht je zurückkommt.
- **Subagent-Tokens in den STATISTIKEN.** Siehe Backlog — ein eigenständiger, älterer Befund,
  der beide Subagent-Sorten betrifft und nicht durch diesen Milestone entsteht.
- **Aufklappbare Detailansicht der Workflow-Agents.** Verworfen: Aggregat ab dem ersten Agent
  ist die Vorgabe.

## Design-Entscheidungen

Zielbild:

```
KONTEXTFENSTER

  34%                                    [Opus]
  ████████████░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░

  ↳ [Opus]        ███████░░░░░░░░░░░░░░   22%     ← normaler Subagent, unverändert
  ⚙ wf_11f45d5b-27d · 12 aktiv  █████░░░░  55%     ← 12 Agents eines Runs, eine Zeile
```

| # | Entscheidung | Begründung |
|---|---|---|
| D-1 | Workflow-Agents kollabieren **ab dem ersten** zu einer Zeile pro Run — nie Einzelbalken | Vorgabe des Nutzers. Löst das Höhenproblem strukturell statt per Top-N/Scrollbereich. |
| D-2 | Der Prozentwert ist das **Maximum**, nicht der Durchschnitt (*bestätigt 2026-08-09*) | 20 Agents auf 5 % und einer auf 95 % ergeben Ø 9 % — beruhigend, während einer in den Autocompact läuft. Der am weitesten fortgeschrittene Agent ist der einzige entscheidungsrelevante Wert. |
| D-3 | **Kein Modell-Badge** in der Workflow-Zeile | Agents eines Runs können unterschiedliche Modelle fahren; der Platz gehört dem Label. |
| D-4 | Klassifizierung über den **Pfad**, nicht über `.meta.json` | Ein String-Check gegen null zusätzliche I/O. Bei 44 Agents × Poll-Tick wäre die Metadatei-Variante messbar teurer, ohne für D-1 etwas beizutragen. |
| D-5 | Mehrere gleichzeitige Runs ⇒ **mehrere Zeilen** (eine pro `wf_`-Ordner) | Fällt aus der Gruppierung nach Ordner ohnehin ab, kein Sonderfall im Code. |
| D-6 | Die **Run-ID wird angezeigt**, wörtlich wie im Dateisystem (`wf_11f45d5b-27d`) — das Wort „Workflow" entfällt dafür (*entschieden 2026-08-09*) | Vorgabe des Nutzers. Wörtlich, damit die ID gegen `/workflows` und den Ordnernamen abgleichbar bleibt. Das Zahnrad-Icon und das `wf_`-Präfix tragen „Workflow" bereits doppelt, und das Label ist die einzige Spalte, die dem `*`-breiten Fortschrittsbalken Platz wegnimmt. Kürzen (z. B. auf `wf_11f45d5b`) ist eine Zeile — erst nach der UAT entscheiden, nicht vorher. |

## Phase 1 — Discovery (Datenschicht)

**`Services/JsonlService.cs`**

1. `FindSubagentFilesForSession` (Zeile 893): `SearchOption.AllDirectories` ergänzen. Damit
   findet **ein** Scan beide Ablageformen; der Fallback-Block (896-905) bleibt unverändert und
   greift weiterhin nur, wenn gar nichts gefunden wurde.
2. Neue private Helper-Methode, die aus dem Dateipfad die Workflow-Run-ID extrahiert: das
   Verzeichnissegment unterhalb von `subagents/workflows/` (z. B. `wf_11f45d5b-27d`).
   Kein Treffer ⇒ `null` ⇒ normaler Subagent.
3. `BuildSubagentContext` (Zeile 910-971) füllt das neue Feld beim Anlegen von
   `SubagentContextData` (Zeile 951).

**`Models/ContextWindowData.cs`**

4. `SubagentContextData` bekommt `public string? WorkflowId { get; init; }`. `null` = normaler
   Subagent. Ein nullable string statt Enum + Zusatztyp — der Wert wird ausschließlich zum
   Gruppieren gebraucht.

**Tests** (`CCInfoWindows.Tests/Services/JsonlServiceSubagentTests.cs`)

5. `ArrangeSubagentFixture` (Zeile 199-225) um einen optionalen `workflowId`-Parameter
   erweitern, der die Datei stattdessen unter `subagents/workflows/{workflowId}/` ablegt.
6. **Achtung `SessionUuidOf` (Zeile 188-189):** der Helper geht zwei `GetDirectoryName`-Hops
   nach oben. Für Workflow-Pfade sind es **vier**. Der Helper muss die Tiefe erkennen, sonst
   liefert er `workflows` als vermeintliche Session-UUID.
7. Neue Fälle: Workflow-Datei wird gefunden · `WorkflowId` korrekt extrahiert · normale Agents
   behalten `WorkflowId == null` · beide Sorten nebeneinander in einer Session · zwei parallele
   Runs bleiben getrennt.

**Abnahme Phase 1:** Ein Test, der eine Workflow-Agent-Datei anlegt, findet sie in
`GetContextWindow(...).Subagents` mit gesetzter `WorkflowId`. Alle bestehenden Subagent-Tests
laufen unverändert grün.

## Phase 2 — Aggregation + UI

**`ViewModels/MainViewModel.cs`**

1. `SubagentDisplayData` (Zeile 24-32) bekommt drei Felder: `Icon` (string — `↳` oder `⚙`),
   `Label` (string — leer bei normalen Subagents) und `IsWorkflow` (bool).
2. Neue **statische** Methode, die `IReadOnlyList<SubagentContextData>` auf die Anzeigezeilen
   abbildet — statisch, damit sie ohne ViewModel-Instanz unit-testbar ist:
   - `GroupBy(s => s.WorkflowId)`
   - Gruppe `null` ⇒ je eine Zeile wie bisher (bestehende Sortierung nach `AgentId` bleibt)
   - Gruppe mit ID ⇒ **eine** Zeile: `Percentage` = Maximum der Gruppe (D-2), `Label` =
     lokalisierter Text aus Run-ID und Anzahl (D-6)
   - **Reihenfolge:** normale Subagents zuerst, danach Workflow-Zeilen nach `WorkflowId`
     sortiert. Deterministisch — dieselbe Anforderung, die Phase 4 der v1.8.3-Spec für die
     Einzelagenten stellte.
3. Aufrufstelle Zeile 1382-1395 auf die neue Methode umstellen.

**Lokalisierung** (`Strings/de-DE/Resources.resw`, `Strings/en-US/Resources.resw`)

4. Ein neuer Key mit **zwei** Platzhaltern, z. B. `WorkflowSubagentLabel` — `{0}` = Run-ID
   wörtlich, `{1}` = Anzahl aktiver Agents. de `{0} · {1} aktiv`, en `{0} · {1} active`.
   Die Run-ID wird **nicht** übersetzt oder umformatiert (D-6).
5. **Der Text darf kein `l:Uids.Uid` im DataTemplate bekommen.** WinUI3Localizer wendet
   Attached-Property-UIDs zur Laufzeit nicht auf dynamisch erzeugte Template-Instanzen an
   (Befund vom 2026-08-08, Beobachtung 7111). Der String wird im ViewModel via
   `GetLocalizedString()` komponiert und formatiert — genau wie `ComputeTooltipText`
   (Zeile 997) es bereits tut — und per `x:Bind` gebunden. Key bleibt **single-segment**.
6. Bekannte Folge: nach einem Sprachwechsel zur Laufzeit aktualisiert sich das Label erst beim
   nächsten Poll-Tick. Akzeptiert — die Sektion wird ohnehin sekündlich neu aufgebaut.

**`Views/MainView.xaml`**

7. Im DataTemplate (Zeile 237-281):
   - Spalte 0: `Text="{x:Bind Icon}"` statt des fest verdrahteten `&#x21B3;`
   - Spalte 1: Badge-`Border` und ein neuer Label-`TextBlock` teilen sich die Zelle, umgeschaltet
     über `IsWorkflow` mit den bereits registrierten `BoolToVisibilityConverter` /
     `InvertedBoolToVisibilityConverter`. **Kein `DataTemplateSelector`** — die vier
     Grid-Spalten passen für beide Zeilentypen unverändert.
   - `Margin="0,4,0,0"` → `"0,2,0,0"` (Wunsch nach kompakteren Abständen)

**Tests**

8. Aggregations-Tests gegen die statische Methode: 12 Workflow-Agents ⇒ eine Zeile mit Anzahl
   12 · `Percentage` entspricht dem Maximum, nicht dem Durchschnitt · zwei Runs ⇒ zwei Zeilen
   mit **je eigener, wörtlich übernommener Run-ID** · gemischte Session ⇒ normale Zeilen zuerst ·
   leere Liste ⇒ keine Zeile.

**Abnahme Phase 2:** Volle Test-Suite grün (Basis: 797 Tests), Release-Build ohne neue Warnungen.

## Phase 3 — Verifikation

1. Release-Build gemäß den strikten Regeln in `CLAUDE.md` (`dotnet build -c Release -o …`,
   **niemals** `dotnet publish`).
2. App starten, in einer Claude-Code-Session einen echten Workflow mit ≥10 Agents auslösen,
   Anzeige gegen das Zielbild oben prüfen.
3. **CPU-Last während des Laufs beobachten.** Bei 44 gleichzeitig schreibenden Agents feuert der
   FileSystemWatcher entsprechend oft; jedes `DataUpdated` löst ein `GetContextWindow` samt
   rekursivem Verzeichnis-Scan aus. Der Debounce sollte das abfangen — falls nicht, ist das der
   Ort für einen Fix, nicht der Scan selbst.
4. Gegenprobe: eine Session mit normalen Subagents (Agent-Tool) zeigt unverändert Einzelbalken.
5. **Breitenprüfung (D-6):** die volle Run-ID im Label darf den Fortschrittsbalken nicht auf
   einen Stummel zusammendrücken — in der Standard-Fenstergröße und mit der deutschen
   Lokalisierung prüfen. Erst hier über ein Kürzen entscheiden, nicht vorab.
6. Screenshots nach `.planning/reviews/` (gitignored), Ergebnis in `.planning/STATE.md`.

## Risiken und Fallstricke

| Risiko | Bewertung |
|---|---|
| Rekursiver Scan pro Poll-Tick wird teuer | **Gering.** Läuft in `Task.Run` (`MainViewModel.cs:1350`), also nicht auf dem UI-Thread; der teure Teil (`ReadTailLines`) wird für alle inaktiven Dateien durch den mtime-Short-Circuit (Zeile 924-929) übersprungen. Der Ordner wächst monoton über die Session-Lebensdauer — bei 77 Dateien irrelevant, ab ~1000 messen. |
| Watcher registriert Workflow-Dateien als Sessions | **Ausgeschlossen.** `IsSubagentFile` (Zeile 880-882) prüft auf das `\subagents\`-Segment, das auch im tieferen Workflow-Pfad steckt; `ProcessSingleFile` verwirft sie vor jeder Registrierung (Zeile 1418). Keine Änderung nötig. |
| `SessionUuidOf` im Test-Helper liefert `workflows` | **Real, siehe Phase 1 Punkt 6.** Fällt sonst als falsch-grüner Test durch. |
| Attached-Property-UID im DataTemplate wirkungslos | **Real, siehe Phase 2 Punkt 5.** Die Tests bestehen trotzdem — der Fehler zeigt sich erst zur Laufzeit als leerer Text. |

## Offene Punkte

Keine. D-2 und D-6 waren die letzten beiden und sind am 2026-08-09 vom Nutzer entschieden
worden. Die einzige verbliebene Nachjustierung ist die Breitenprüfung in Phase 3 Punkt 5 —
und die ist eine Messung, keine offene Frage.
