## ⚠ Der ganze Milestone ist eine Windows-Erweiterung, keine Parität

Die Anzeige von Workflow-Subagents **existiert in der originalen macOS-App
([stefanlange/ccInfo](https://github.com/stefanlange/ccInfo)) nicht** — weder die Zeile, noch das
Zahnrad, noch die Aggregation, noch der Tooltip aus Phase 4. `spec/` (v1.7.1 … v1.11.1) enthält
keinen einzigen Treffer für „workflow"; Workflows sind ein neueres Claude-Code-Feature als die
Referenz-App.

**Konsequenz für künftige Parity-Abgleiche:** Findet sich upstream irgendwann eine eigene
Workflow-Darstellung, ist das **kein Fix eines Rückstands**, sondern eine Kollision mit einer
bereits getroffenen Windows-Entscheidung. Erst vergleichen, dann entscheiden — nicht blind
angleichen. Dieselbe Notiz steht im Code an jeder Stelle, die dieses Feature trägt —
grepbar über `Windows-only`.

## Context

Startet Claude Code einen Workflow (`ultracode`), erscheint **kein einziger** seiner Subagents
in der KONTEXTFENSTER-Sektion. Normale Subagents (via Agent-Tool) werden korrekt angezeigt.

### Ursache

`FindSubagentFilesForSession` (`JsonlService.cs:885-908`) scannt mit
`Directory.GetFiles(subagentDir, AgentFilePattern)` — ohne `SearchOption`, also
**nur die oberste Ebene**. Die beiden Ablageformen unterscheiden sich aber in der Tiefe:

```
{projectDir}/{sessionUuid}/subagents/agent-{id}.jsonl                      ← Agent-Tool, gefunden
{projectDir}/{sessionUuid}/subagents/workflows/wf_{runId}/agent-{id}.jsonl ← Workflow, NICHT gefunden
```

Ein Workflow-Run legt außerdem `{projectDir}/{sessionUuid}/workflows/wf_{runId}.json` an — ein
**anderes** `workflows`-Verzeichnis, eine Ebene höher. Für Phase 1 irrelevant (dort liegen keine
Transkripte), ab Phase 4 die Quelle für Name, Beschreibung und Startzeit. Details dort.

Der Scan liefert für eine reine Workflow-Session null Treffer. Weil danach `result.Count == 0`
gilt, greift der Fallback auf `{projectDir}/subagents` (Zeile 896-905) — ein Verzeichnis, das
in dieser Ablage nicht existiert. Ergebnis: leere Liste, kein Log-Eintrag, keine sichtbare
Fehlermeldung. Der Bug ist **stumm**.

### Gemessene Größenordnung (2026-08-09)

| Wert | Messung |
|---|---|
| Workflow-Agent-Dateien gesamt | 67 in 7 Runs |
| Größter einzelner Run | **44 Agents** |
| Flache Subagent-Dateien | 10 |

Ein Run kann also die Zeilenzahl der Sektion vervierzigfachen. Bei ~28 px pro Zeile wären
44 Agents ≈ 1230 px in einem ~600 px hohen Fenster. Deshalb ist die Anzeige-Entscheidung
(unten) kein Kosmetik-Thema, sondern die eigentliche Substanz des Milestones.

### macOS-Referenz: kein Vorbild vorhanden

`spec/` (v1.7.1, v1.8.3, v1.10.0, v1.11.1) enthält **keinen einzigen** Treffer für „workflow".
Die Subagent-Anforderungen FA-042 und FA-062 sowie Phase 4 der v1.8.3-Spec (Sortierstabilität)
kennen ausschließlich den flachen Pfad. Workflows sind ein neueres Claude-Code-Feature als die
Referenz-App.

**Konsequenz:** Dieser Milestone ist eine Windows-Erweiterung *über* die Parität hinaus, kein
Nachzug. Es gibt kein Upstream-Design, an dem man sich orientieren müsste oder von dem man
abweichen würde.

### Ausdrücklich NICHT im Scope

- **Agent-Namen aus `.meta.json`.** Neben jeder `agent-*.jsonl` liegt eine bisher ungenutzte
  Metadatei — normal `{"agentType":"Explore","description":"Map chart implementation",…}`,
  Workflow `{"agentType":"workflow-subagent","spawnDepth":1}`. Sie würde erlauben, endlich
  echte Namen statt Hex-IDs zu zeigen. Bewusst ausgelassen: die gewählte Aggregat-Darstellung
  braucht keine Namen, und das Lesen kostete 44 Dateiöffnungen pro Poll-Tick. Bleibt als
  Option, falls die Einzelagenten-Ansicht je zurückkommt.
- **Subagent-Tokens in den STATISTIKEN.** Siehe Backlog — ein eigenständiger, älterer Befund,
  der beide Subagent-Sorten betrifft und nicht durch diesen Milestone entsteht.
- **Aufklappbare Detailansicht der Workflow-Agents.** Verworfen: Aggregat ab dem ersten Agent
  ist die Vorgabe.

## Design-Entscheidungen

Zielbild **nach Phase 3b** (der Balken in der Workflow-Zeile ist entfallen, siehe D-7):

```
KONTEXTFENSTER

  34%                                    [Opus]
  ████████████░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░

  ↳ [Opus 5]      ███████░░░░░░░░░░░░░░   22%     ← normaler Subagent, unverändert
  ⚙ wf_eda3abc2-8c9 · 31/31 Agents fertig · 3.3M Tokens
                                                  ← ein Run, eine Zeile, kein Balken
```

Ursprüngliches Zielbild aus Phase 2 (historisch, **nicht** mehr der Ist-Zustand):
`⚙ wf_11f45d5b-27d · 12 aktiv  █████░░░░  55%`

| # | Entscheidung | Begründung |
|---|---|---|
| D-1 | Workflow-Agents kollabieren **ab dem ersten** zu einer Zeile pro Run — nie Einzelbalken | Vorgabe des Nutzers. Löst das Höhenproblem strukturell statt per Top-N/Scrollbereich. |
| D-2 | ~~Der Prozentwert ist das **Maximum**, nicht der Durchschnitt~~ **überschrieben 2026-08-11 durch D-7** | Die Begründung war korrekt, die Frage falsch gestellt: `Utilization` ist ein Verhältnis gegen eine **Pro-Agent**-Obergrenze. Über eine Gruppe existiert diese Obergrenze nicht — 43 Agents haben 43 Fenster —, also erzeugen Maximum, Mittelwert und Summe gleichermaßen eine Zahl ohne Bezugsgröße. D-2 war die Wahl zwischen zwei falschen Antworten. |
| D-3 | **Kein Modell-Badge** in der Workflow-Zeile | Agents eines Runs können unterschiedliche Modelle fahren; der Platz gehört dem Label. |
| D-4 | Klassifizierung über den **Pfad**, nicht über `.meta.json` | Ein String-Check gegen null zusätzliche I/O. Bei 44 Agents × Poll-Tick wäre die Metadatei-Variante messbar teurer, ohne für D-1 etwas beizutragen. |
| D-5 | Mehrere gleichzeitige Runs ⇒ **mehrere Zeilen** (eine pro `wf_`-Ordner) | Fällt aus der Gruppierung nach Ordner ohnehin ab, kein Sonderfall im Code. |
| D-6 | Die **Run-ID wird angezeigt**, wörtlich wie im Dateisystem (`wf_11f45d5b-27d`) — das Wort „Workflow" entfällt in der Zeile (*entschieden 2026-08-09, Balken-Begründung entfallen 2026-08-11, Kürzen verworfen*) | Vorgabe des Nutzers. Wörtlich, damit die ID gegen `/workflows` und den Ordnernamen abgleichbar bleibt. Das Zahnrad und das `wf_`-Präfix tragen „Workflow" bereits doppelt. Die zweite Begründung („nimmt dem Balken Platz weg") ist mit D-7 gegenstandslos. Das Wort „Workflow" kommt in Phase 4 im **Tooltip** — dort kostet es keine Zeilenbreite. Kürzen bleibt verworfen: die ID muss abgleichbar bleiben, und `TextTrimming` deckt schmale Fenster ab. |

### Nachträge Phase 3b (2026-08-11) und Phase 4 (2026-08-12)

| # | Entscheidung | Begründung |
|---|---|---|
| D-7 | Die Workflow-Zeile verliert **Balken und Prozentwert** und trägt stattdessen `{done}/{started} Agents fertig · {tokens} Tokens` | `N/M fertig` und die Token-Summe sind **extensive** Größen: sie addieren sich über eine Gruppe sauber, ein Verhältnis gegen eine nicht existierende Gruppen-Obergrenze nicht (siehe D-2). Genau deshalb zeigt die CLI diese beiden Werte. Erledigt Review-Befund G-1 (Gruppen-Maximum nur über 30-s-frische Agents) und D-1 (Label drückt die geteilte Balkenskala) durch Wegfall. |
| D-8 | Der **Nenner wächst während des Runs** (`started` = bisher gespawnt, kein Plansoll) | Ausdrücklich vom Nutzer bestätigt. Ein Skript, das 8 Finder, dann 21 Verifier, dann 1 Kritiker fächert, zeigt `3/8`, später `9/29`. Entspricht dem, was das Workflow-Tool selbst berichtet. |
| D-9 | Der Staleness-Gate (30 s) gilt **pro Run**, nicht pro Agent | Gemessen, nicht geschätzt: ein fertiger Agent schreibt nicht mehr und fällt aus dem Gate — die Summe verliert genau die Agents, die sie braucht. Gegen den echten 43-Agent-Run zeigte der Pro-Agent-Gate im **Median 22,3 %** der wahren Summe und **4,4 %** im letzten Snapshot, den G-2 stundenlang stehen lässt. Ein toter Run öffnet weiterhin keine Datei, die Kosten wachsen also nicht mit fertigen Runs. |
| D-10 | Das dekorative `↓` vor der Token-Zahl **entfällt** | Es zu behalten kostet entweder ein zweites Element (zerstört `TextTrimming` über die Zeile) oder `FontFamily="Segoe UI Symbol"` für den gesamten Label-Text (ändert die Schrift von Run-ID und Wörtern). Es trug keine Information. |
| D-11 | Glyphen kommen als **`\uXXXX`-Escapes** in den Code, die Schrift wird im Template auf `Segoe UI Symbol` festgenagelt | Review-Befund D-2 (Kontrast), gemessen: über DWrite-Fallback landet U+2699 in **Segoe UI Emoji**, einer Farbschrift, die `Foreground` ignoriert — 202 verschiedene Farben im Zahnrad-Ausschnitt, hellster Pixel (228,222,239) statt der deklarierten `#636366`. Nach dem Fix: 15 Farben, hellster Pixel (99,99,102) = exakt `#636366`. Escapes zusätzlich, weil eine PowerShell-Massenänderung in diesem Repo schon einmal Non-ASCII zerstört hat. |
| D-12 | **Tooltip beim Hovern** über die Workflow-Zeile mit Typ, Name, Beschreibung, ID, fertigen Agents, Startzeit und Kontextgröße — jeder Wert mit Label (*Phase 4, offen*) | Vorgabe des Nutzers. Die Zeile ist auf eine Breite begrenzt und trimmt; der Tooltip ist der Ort für die Werte, die dort nicht hinpassen — insbesondere die Zeitangabe, die es bisher nirgends gibt. |
| D-13 | **Keine Aktiv-Zahl** im Tooltip — nur `Agents: {done}/{started} fertig` (*entschieden 2026-08-12, ersetzt die vorige Fassung*) | Vorgabe des Nutzers. Trägt auch inhaltlich: die Zahl wäre redundant (`30 − 29 = 1` steht direkt daneben), und jede *andere* Definition von „aktiv" wäre „hat in den letzten 30 s geschrieben" — genau die Zahl, die der Review als irreführend nachgewiesen hat (das alte „43 aktiv" blieb nach Run-Ende stundenlang stehen, G-2). Nicht anzeigen ist hier billiger und ehrlicher als definieren. |
| D-14 | **Startzeitpunkt statt Laufzeit** im Tooltip, mit **Datum und Uhrzeit** (*entschieden 2026-08-12*) | Vorgabe des Nutzers, nachdem beide Varianten und die Kombination gegenübergestellt wurden. Technisch die schlankere Hälfte: **keine** neue Formatier-Methode (`FormatWithPattern` ist fertig, gehärtet und über `FormatNextWindowLabel` präzedenzbelegt), kein Formatwechsel `40s`/`21m 40s`/`1h 05m`, kein Klemmen negativer Differenzen. Das Datum kam auf Nutzerwunsch hinzu und erledigt die Mitternachts-Uneindeutigkeit gleich mit. Bewusst in Kauf genommen: „wie lange läuft das schon" muss der Betrachter selbst rechnen. |
| D-15 | **Name und Beschreibung** aus `workflows/wf_{runId}.json` in den Tooltip, wörtlich (*entschieden 2026-08-12*) | Vorgabe des Nutzers. Erst dadurch sagt die Zeile, *was* der Run tut — `wf_eda3abc2-8c9` allein ist nicht deutbar. Beide Felder sind top-level (`workflowName`, `summary`), das JS-Skript muss also nicht geparst werden. Die Werte werden **nicht übersetzt**: Fremdtext aus einem Skript, keine UI-Zeichenketten. Die Labels davor schon (D-17). |
| D-16 | Die Metadatei ist die Quelle für `startTime`, **`timestamp` ist tabu**, und die Anzeige **degradiert** ohne sie (*Messung 2026-08-12*) | Gemessen: `timestamp == json ctime == json mtime == startTime + durationMs`, also der **Abschluss**zeitpunkt — wer es als Startzeit nimmt, zeigt bei jedem Run die falsche Uhrzeit. Und weil die Datei erst beim Abschluss entsteht, sind Name und Beschreibung während der ganzen Laufzeit nicht verfügbar. Der Tooltip lässt die zwei Zeilen dann weg (kein Platzhalter, keine leere Zeile), die Startzeit fällt auf die Verzeichnis-Erstellzeit zurück (+2–4 s). Alternative wäre gewesen, den Namen aus dem Skript-Dateinamen zu ziehen — verworfen, weil nur 5 von 8 Runs eine Skript-Datei haben. |
| D-17 | **Jeder Wert im Tooltip trägt ein Label** — `ID:`, `Name:`, `Beschreibung:`, `Agents:`, `Start:`, `Kontext:` (*entschieden 2026-08-12*) | Vorgabe des Nutzers: eine nackte `wf_eda3abc2-8c9` oder ein nacktes `3.3M Tokens` sagt nicht, was der Wert darstellt. Die Zeile in der Sektion darf knapp bleiben, weil sie unter dem Zahnrad und neben ihren Nachbarn im Kontext steht; ein Tooltip wird isoliert gelesen und muss sich selbst erklären. |
| D-18 | Das Token-Label heißt **`Kontext:`**, ausdrücklich **nicht** „Verbrauch" (*Messung 2026-08-12*) | Der Wert ist die Summe der **finalen Kontextgrößen** aller Agents des Runs, nicht der Durchsatz. Gemessen an `wf_eda3abc2-8c9`: angezeigt 3.252.640, kumulativ verbraucht (input + cache_read + cache_create + output über alle 1377 Assistant-Einträge) **112.654.074** — Faktor **34,6**. Ein Label „Verbrauch" wäre also nicht ungenau, sondern um eine Größenordnung falsch. „Kontext" ist zusätzlich der Begriff, den die Sektion („KONTEXTFENSTER") ohnehin verwendet. |

## Phase 4 — Tooltip auf der Workflow-Zeile (umgesetzt 2026-08-12)

### Datenschicht: die Run-Metadatei — und ihre drei Fallstricke

Es gibt eine **zweite, bisher unbeachtete Datei** pro Run, an einem anderen Ort als die Transkripte:

```
{projectDir}/{sessionUuid}/workflows/wf_{runId}.json          ← Metadatei, hier neu erschlossen
{projectDir}/{sessionUuid}/workflows/scripts/{name}-wf_{runId}.js
{projectDir}/{sessionUuid}/subagents/workflows/wf_{runId}/    ← Agent-Transkripte + journal.jsonl
```

Sie trägt genau die gewünschten Felder — top-level, ohne das JS-Skript parsen zu müssen:

| Feld | Beispiel | Verwendung |
|---|---|---|
| `workflowName` | `review-v16-to-v17` | Name im Tooltip |
| `summary` | `Multi-dimensional review (…) of the v1.6.0..HEAD diff` | Beschreibung im Tooltip; **identisch** mit `meta.description` im Skript (verifiziert) |
| `startTime` | `1786281584186` (Unix-**Millisekunden**) | Startzeitpunkt |
| `timestamp` | `2026-08-09T13:52:33.283Z` | **NICHT der Start** — siehe Fallstrick 1 |

Abdeckung geprüft: **8 Run-Verzeichnisse, 8 Metadateien, keine Lücke** in beide Richtungen.

**Fallstrick 1 — `timestamp` ist das Run-ENDE, nicht der Start.** Dreifach belegt:
`json ctime == json mtime == timestamp` bei allen 8 Runs; `startTime + durationMs == timestamp`
(1969095 ms gegen 1969,097 s gemessene Differenz, 2 ms Abweichung); und `startTime` deckt sich mit
der Verzeichnis-Erstellzeit. Wer `timestamp` nimmt, zeigt den Zeitpunkt an, an dem der Run *fertig*
war. Das gesuchte Feld ist **`startTime`**, und es ist Unix-Millisekunden, kein ISO-String:
`DateTimeOffset.FromUnixTimeMilliseconds(startTime)`.

**Fallstrick 2 — die Datei existiert erst NACH Run-Ende.** `ctime == mtime == Endzeitpunkt` bei allen
8 Runs heißt: sie wird einmal geschrieben, wenn der Run abschließt (NTFS-Tunneling ist als Erklärung
ausgeschlossen, zwischen Start und Ende liegen 22–39 Minuten). Während der gesamten Laufzeit ist sie
nicht da. **Konsequenz: Name und Beschreibung sind genau dann nicht verfügbar, wenn die Zeile am
nützlichsten ist.** Der Tooltip muss ohne sie funktionieren und die beiden Zeilen weglassen, nicht
Platzhalter zeigen.

Für die **Startzeit** gibt es dagegen einen Ersatz, der ab der ersten Sekunde trägt — gemessen gegen
zwei Runs mit unabhängig bekannter Wall-Clock (die Dauer ist der Prüfwert, nicht das Anzeigeziel):

| Quelle | verfügbar | wf_11f45d5b-27d | wf_eda3abc2-8c9 |
|---|---|---|---|
| `startTime` aus der Metadatei | **erst nach Run-Ende** | 10:25:05 | 15:19:44 |
| `Directory.GetCreationTimeUtc(runDir)` | **ab Run-Start** | 10:25:09 (+4 s) | 15:19:46 (+2 s) |
| Skript-Datei-Erstellzeit | ab Run-Start, aber **nur 5 von 8 Runs** | 10:25:05 | 15:19:44 |

Gewählt: **`startTime` wenn die Metadatei da ist, sonst die Verzeichnis-Erstellzeit.** Zwei Zeilen
Fallback, dafür ist die Startzeit immer vorhanden und im Nachhinein exakt. Die Skript-Datei fällt
aus: 5/8 Abdeckung (Runs, die über `scriptPath` oder einen gespeicherten Namen starten, legen keine
neue ab), und die Beschreibung wäre nur per JS-Regex zu holen.

**Fallstrick 3 — die Datei ist 45–190 KB groß** (gemessen über alle 8: Median ≈ 100 KB). Der Grund
sind `script`, `result`, `logs` und `workflowProgress`; die vier gebrauchten Felder liegen teilweise
*hinter* diesen großen Blöcken, ein Early-Out mit `Utf8JsonReader` bringt also nichts.
**Deshalb ist Caching hier Pflicht, nicht Optimierung:** `workflowName`, `summary` und `startTime`
sind pro Run unveränderlich, also einmal lesen und in einem `ConcurrentDictionary<string, …>` auf die
Run-ID halten. Ein Fehlschlag (Datei noch nicht da) darf **nicht** als Negativ-Ergebnis gecacht
werden, sonst bleibt der Name nach Run-Ende für den Rest der Sitzung leer.

1. **`Models/ContextWindowData.cs`** — `SubagentContextData` bekommt drei Felder:
   `RunStartedUtc` (`DateTimeOffset`), `RunName` (`string?`), `RunDescription` (`string?`).
   `default`/`null` für Plain-Agents und für Runs ohne Metadatei.
2. **`Services/JsonlService.cs`** — neue `ReadWorkflowMetadata(runId, sessionDir)` neben

### Abnahme Phase 4

Volle Suite grün (Basis: 818). Im laufenden Programm gegen einen bekannten Run geprüft: Tooltip
erscheint beim Hover über die Workflow-Zeile, **nicht** über eine Plain-Zeile, zeigt Name und
Beschreibung des Runs, und die Startzeit stimmt mit `startTime` der Metadatei in **lokaler** Zeit
überein. Für `wf_eda3abc2-8c9` ist das prüfbar gegen bekannte Werte: `review-v16-to-v17`,
`Multi-dimensional review (…)`, Start `2026-08-09T13:19:44.186Z` = lokal **15:19**.

**Das Fixture-Verfahren muss dafür erweitert werden.** Bisher wurde nur
`subagents/workflows/wf_x/` in die aktive Session kopiert; die Metadatei liegt an einem *anderen*
Ort und muss mit:

```
<session>/subagents/workflows/wf_x/      (Agent-Transkripte + journal.jsonl, mtime +20 min)
<session>/workflows/wf_x.json            (Metadatei — NEU, sonst kein Name/Beschreibung)
```

Angenehmer Nebeneffekt: weil `startTime` aus dem *Dateiinhalt* kommt, zeigt das Fixture die echte
Startzeit des Originalruns — anders als bei der Verzeichnis-Erstellzeit, die das Kopieren auf
„jetzt" setzt. Beides danach wieder löschen; App vorher stoppen, sie hält Leseschleifen.

Zusätzlich zu prüfen: ein Run **ohne** Metadatei (nur das `subagents/`-Verzeichnis kopieren) zeigt
den Tooltip ohne Name- und Beschreibungszeile und mit der Verzeichnis-Erstellzeit als Start — das ist
der Zustand jedes laufenden Runs und damit der häufigere von beiden.

| Tooltip aktualisiert sich nicht, während er offen steht | **Mit D-14 gegenstandslos.** WinUI liest den Text beim Öffnen; eine Startzeit ändert sich nie. Das war der Fallstrick der Laufzeit-Variante und ist ein stiller Vorteil der gewählten. |
