## v1.9.0 Changes (2026-03-31)

### Feature 1: Settings Sidebar Redesign

**What changed:** The Settings window was redesigned from a `TabView` to a `NavigationSplitView` sidebar layout with colored icon badges.

**Implementation details (from source):**

1. **SettingsTab enum** defines four tabs:
   - `general` (green badge, gear icon)
   - `updates` (blue badge, arrow.triangle.2.circlepath icon)
   - `account` (red badge, person.crop.circle icon)
   - `about` (orange badge, info.circle icon)

2. **SettingsIconBadge component** renders a 22x22 colored rounded rectangle badge containing a white SF Symbol icon (12pt semibold, cornerRadius 5).

3. **Layout:** `NavigationSplitView` with `.balanced` style:
   - Sidebar: `List` with `.sidebar` style, 150-200pt width
   - Detail: Dynamic content switching based on selected tab with inline title heading
   - Toolbar toggle button removed from sidebar
   - Hidden toolbar backgrounds in detail area

4. **Window size** increased from 400x365 to **580x380** pixels.

5. **About tab** now includes the app icon.

**Windows port considerations:**
- WinUI 3 has `NavigationView` which supports a similar sidebar pattern
- Icon badges need to be recreated with colored rounded rectangle + white icon overlay
- Window size change is straightforward
- Tab content (General, Updates, Account, About) already exists in ccInfoWin; layout change only

### Feature 2: Horizontal Color Gradient on Usage Chart

**What changed:** The flat green chart fill was replaced with a smooth horizontal color gradient that follows usage level (green -> yellow -> orange -> red).

**Implementation details (from source):**

1. **Color thresholds** (defined in `UtilizationThresholds`):
   - 0-50%: Deep green -> green -> yellow
   - 50-75%: Yellow -> orange
   - 75-90%: Orange -> red
   - 90-100%: Red

2. **`buildColorLookup()`** generates a 101-element color array (index 0-100) using `colorForUsage()` which interpolates between RGB values through four gradient stops. Dark mode applies 15% desaturation.

3. **`horizontalGradientStops()`** function:
   - Takes data points, window start time, chart width, and color lookup
   - Maps each data point's X position to its usage color
   - Normalizes positions to 0.0-1.0 range: `location = (x - minX) / range`
   - Returns gradient stops plus start/end fractions
   - Deduplicates stops at identical locations

4. **`buildContinuousPaths()`** function:
   - Two modes: closed (filled area) and open (line stroke)
   - Closed mode creates area shapes with baseline at chart bottom
   - Open mode creates line strokes for outline
   - Both skip segments where `isGap == true` or both points have zero usage
   - Splits paths at data gaps for visual discontinuities

5. **Rendering:**
   - Area fill: `LinearGradient` at 25% opacity
   - Line stroke: `LinearGradient` at full opacity, lineWidth 2.5 (shareable) / 1.5 (live)
   - Gradient spans only the actual data region, not the full chart width

**Windows port considerations:**
- Win2D `CanvasLinearGradientBrush` supports gradient stops in the same way
- Need to port the `colorForUsage()` interpolation logic
- Path building with gap handling translates to Win2D geometry paths
- The live chart (`UsageChartView`) and export chart (`ShareableChartView`) both use this pattern

### Feature 3: Chart Gap Fix After App Restart

**What changed:** Visual gaps in the usage chart after app restart were fixed.

**Implementation details (from source):**

1. **Root cause:** When usage history was persisted to disk and reloaded, `isGap` markers from previous sessions would show as visual gaps in the chart. These gaps represent app restarts, not actual usage pauses — the API-reported utilization is continuous regardless of whether ccInfo was running.

2. **Fix in `UsageHistoryService`:** On `loadFromDisk()`, the service strips `isGap` flags from persisted data before rendering:
   ```
   // Strip isGap flags from persisted data — gaps from previous sessions
   // represent app restarts, not actual usage pauses.
   ```

3. **Gap detection only applies to current session:** The 90-second threshold (3x the 30-second poll interval) for inserting gap markers only applies to the live recording, not to reloaded history.

**Windows port considerations:**
- Already have `UsageHistoryService` equivalent; need to add gap stripping on load
- Simple data transformation when deserializing persisted history

### Feature 4: Performance Optimizations (CPU, I/O)

**What changed:** Multiple performance improvements to reduce CPU usage during active Claude sessions.

#### 4a: FSEvents Directory-Level Coalescing
- Replaced per-file FSEvents monitoring with directory-level coalescing
- Reduced filesystem event overhead

**Windows port:** Uses `FileSystemWatcher` — review if similar coalescing is needed.

#### 4b: Caching (parsed paths, context windows, JSONL byte offsets)
- Added caches for:
  - Parsed session directory paths
  - Context window states
  - JSONL byte offsets (for incremental parsing)

**Windows port:** Implement equivalent caching in service layer.

#### 4c: Incremental JSONL Parsing
**Implementation details (from source):**

1. **`FileParseState` struct** tracks per-file state:
   - `byteOffset`: Current position in file
   - `accumulator`: Token accumulation state
   - `fileSize`: Last known file size
   - `filterDate`: For cache validation

2. **`incrementalParse()` method:**
   - Uses `stat()` for fast file size checks (avoids opening FileHandle for unchanged files)
   - Validates cache by comparing stored `fileSize` and `filterDate`
   - Seeks to last position: `handle.seek(toFileOffset: startOffset)`
   - Reads only new bytes: `readDataToEndOfFile()`

3. **Partial line handling:**
   - Detects incomplete lines at file boundaries
   - Backs up byte offset to re-read incomplete lines on next call
   - Prevents data corruption from mid-line reads

4. **Memory optimization:**
   - Clears dedup hashes from previous chunks (offset prevents re-reading)
   - Cache limited to 200 files, evicts oldest entries when exceeded

**Windows port considerations:**
- .NET `FileStream` with `Seek()` provides same capability
- Partial line handling logic needs careful porting
- Cache eviction strategy should match (200 file limit)

#### 4d: Single-Pass Session Discovery
- Combined two separate directory walks into a single pass
- Reduces I/O during session enumeration

**Windows port:** Review current session discovery for similar optimization.

#### 4e: Menu Bar Rendering Skip
- Optimized to skip redundant menu bar re-renders when values haven't changed
- Uses cache key comparison

**Windows port:** Taskbar/tray icon rendering may benefit from similar optimization.

### Feature 5: AppState Migration to @Observable

**What changed:** Migrated `AppState` from `ObservableObject` to Swift's `@Observable` macro for fine-grained re-renders.

**Windows port:** N/A — this is a SwiftUI-specific optimization. The CommunityToolkit.Mvvm `[ObservableProperty]` pattern already provides granular property-level change notification.

## v1.10.0 Changes (2026-04-12)

### Feature 7: Burn Rate Warning System

**What changed:** Added burn rate projection that warns users when their current token consumption pace will exhaust the 5-hour window before it resets. Three visual indicators: menu bar flame icon, red inline banner in popover, and one-shot macOS notification.

This is the **most significant new feature** to port.

#### 7a: BurnRateCalculator (Prediction Engine)

**Complete algorithm (from source):**

```csharp
// Pseudocode translation of BurnRateCalculator.predict()

// Input: usageHistory, currentUtilization (0-100), resetsAt (DateTime)

// Guard 1: Need resetsAt in the future
if (resetsAt == null || resetsAt <= now) return null;

// Guard 2: Skip trivial usage levels (below 20%)
if (currentUtilization < 20) return null;

// Collect non-gap points from the last 15 minutes
var cutoff = now - TimeSpan.FromMinutes(15);
var recentPoints = history
    .Where(p => !p.IsGap && p.Timestamp >= cutoff)
    .ToList();

// Guard 3: Need at least 3 data points
if (recentPoints.Count < 3) return null;

// Linear regression: slope in usage-percent per second
var referenceTime = recentPoints[0].Timestamp;
var pairs = recentPoints.Select(p => (
    x: (p.Timestamp - referenceTime).TotalSeconds,
    y: (double)p.Usage
)).ToList();

var n = (double)pairs.Count;
var sumX = pairs.Sum(p => p.x);
var sumY = pairs.Sum(p => p.y);
var sumXY = pairs.Sum(p => p.x * p.y);
var sumXX = pairs.Sum(p => p.x * p.x);

var denominator = n * sumXX - sumX * sumX;
if (Math.Abs(denominator) <= 0) return null;

var slope = (n * sumXY - sumX * sumY) / denominator;

// Guard 4: Usage must be increasing
if (slope <= 0) return null;

// Project time until 100%
var remaining = 100.0 - currentUtilization;
var secondsToLimit = remaining / slope;
if (secondsToLimit <= 0) return null;

var hitsLimitAt = now + TimeSpan.FromSeconds(secondsToLimit);

// Guard 5: Only warn if projected exhaustion is BEFORE the window resets
if (hitsLimitAt >= resetsAt) return null;

var minutesUntilLimit = Math.Max(1, (int)(secondsToLimit / 60));
return new Prediction(hitsLimitAt, minutesUntilLimit);
```

**Key thresholds:**
- Minimum 20% current utilization to even consider warning
- 15-minute lookback window for data points
- Minimum 3 data points required for regression
- Only warns if projected exhaustion is before window reset time
- Positive slope (increasing usage) required

**Prediction struct:**
- `HitsLimitAt` (DateTime): When 100% will be reached
- `MinutesUntilLimit` (int): Minutes until limit, minimum 1
- `FormattedTimeUntilLimit` (string): Human-readable format
  - >= 60 min: `~Xh YYmin` (e.g., "~1h 23min") or `~Xh` if minutes == 0
  - < 60 min: `~Xmin` (e.g., "~33min")

#### 7b: Menu Bar Flame Icon

**Implementation details:**
- SF Symbol `flame.fill` rendered at 75% of bar height
- 5-point gap between flame and usage percentage bars
- Dark mode: white flame; Light mode: black flame
- Left-aligned flame, right-aligned bars
- Uses `ctx.translateBy()` to shift bar content rightward

**Rendering logic:**
- `MenuBarCacheKey` extended with `showFlame: Bool` and `isDark: Bool`
- `showFlame` is computed by calling `BurnRateCalculator.predict()` on each render
- `MenuBarImageRenderer.renderWithFlame()` draws the flame + bars

**Windows port considerations:**
- Tray icon rendering uses different mechanism (system tray NotifyIcon)
- May need a custom-rendered tray icon or overlay approach
- Alternative: Change tray icon to a warning variant when burn rate active
- Consider WinUI 3 tray icon capabilities

#### 7c: Red Inline Banner in Popover

**Implementation details (from source):**

```
BurnRateWarningBanner view:
- HStack with spacing: 5
- flame.fill icon in white
- Text: "Token limit reached in {timeLabel}" (localized)
- Font: .caption
- ForegroundStyle: .white
- Spacer (pushes content left)
- Padding: horizontal 8, vertical 4
- Background: Color.red
- ClipShape: RoundedRectangle(cornerRadius: 6)

**Placement:** Conditionally displayed inside the 5-hour window section, between the chart/utilization display and the weekly limit section:

if let prediction = BurnRateCalculator.predict(

}
```

**Screenshot confirmation:** The screenshot shows the banner as:

**Windows port considerations:**
- Implement as a `Border` with red `Background` inside the 5-hour section
- `FontIcon` glyph for flame (or a custom icon)
- Match the corner radius, padding, and typography

#### 7d: macOS Notification (One-Shot)

**Implementation details (from NotificationService.swift):**

```swift
// checkBurnRate is called during each refresh cycle
func checkBurnRate(history: [UsageDataPoint], usage: UsageData) {
    // Compute prediction
    guard let prediction = BurnRateCalculator.predict(...) else {
        notifiedBurnRate = false  // Reset flag when no warning
        return
    }
    guard !notifiedBurnRate else { return }  // Already sent this cycle
    notifiedBurnRate = true

    // Send notification
    content.title = "Burn rate warning"
    content.body = "At current pace, token limit reached in {timeLabel}."
    content.sound = .default
    content.interruptionLevel = .timeSensitive
    // identifier: "usage-burnrate"
}
```

**One-shot behavior:**
- `notifiedBurnRate` boolean flag prevents re-notification
- Flag resets to `false` when prediction becomes nil (usage dropped or window reset)
- Also reset via `resetAllThresholds()` on app restart/sign out

**Windows port considerations:**
- Use Windows Toast Notifications (Microsoft.Toolkit.Uwp.Notifications or WinUI 3 AppNotificationManager)
- Same one-shot pattern with boolean flag
- Need to handle Windows notification permissions

### Feature 8: Session Dropdown Fix

**What changed:** Fixed session dropdown occasionally displaying encoded project path instead of readable project name.

**Implementation details:**
- Root cause: Directory-level FSEvents missed individual file changes that update session metadata
- Fix: Added `kFSEventStreamCreateFlagFileEvents` flag to FSEventStream creation
- This enables file-level event granularity instead of directory-level batching

**Windows port considerations:**
- Review `FileSystemWatcher` configuration in ccInfoWin
- Ensure `NotifyFilter` includes `FileName | LastWrite` for file-level events
- Check if similar stale display issues exist in the Windows session dropdown

## Suggested Porting Order

### Phase 1: Burn Rate Warning (v1.10.0 parity)
1. Port `BurnRateCalculator` as a static utility class
2. Add burn rate banner to MainView (5-hour section)
3. Implement Windows toast notification with one-shot behavior
4. Update tray icon when burn rate warning active

**Rationale:** This is the headline feature of v1.10.0 and the most user-visible change. The algorithm is well-defined and self-contained.

### Phase 2: Chart Gradient (v1.9.0 parity)
1. Implement `ChartDrawingHelper.BuildColorLookup()` with RGB interpolation
2. Implement `HorizontalGradientStops()` for gradient mapping
3. Update chart rendering to use `CanvasLinearGradientBrush`
4. Handle gap splitting in path construction
5. Apply to both live chart and export chart

**Rationale:** Visually impactful but requires Win2D gradient rendering which is more complex.

### Phase 3: Settings Redesign + Bug Fixes
1. Redesign SettingsView with NavigationView sidebar
2. Add colored icon badges to settings tabs
3. Fix chart gap on reload (strip isGap flags)
4. Review session dropdown for file-level watcher fix

**Rationale:** Lower priority UX polish that can be done after core features.

### Phase 4: Performance Optimizations
1. Incremental JSONL parsing
2. Caching layer
3. Other I/O optimizations

**Rationale:** Only needed if performance issues are observed on Windows.
